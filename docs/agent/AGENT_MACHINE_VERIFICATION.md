# AGENT_MACHINE_VERIFICATION.md: no human verifier in the loop (explicitly requested by Mri)

Read after AGENT_RISK_CONTROLS.md. This file overrides every instruction that requires a human to approve provisions or conditions. Mri has explicitly asked for a fully automated path and approves the one gate change described below.
All other AGENTS.md hard rules still apply.

## The one honesty rule
Nothing automated may ever be labelled `human_verified`, and `reviewed_by` / `reviewed_at` must never be filled with a person's name by code. Automated verification gets its own status, `machine_verified`, with the evidence recorded. The UI, API, results and submission notes must say "machine-verified, not reviewed by a lawyer or human" wherever corpus status is shown. If any code path writes a human status automatically, that is a critical defect.

## Status model (change, approved by Mri)
- `review_status`: `unverified` | `machine_verified` | `human_verified` | `rejected`
- A `machine_verified` provision has: `verified_by: "machine"`, `verification_method_count`, `verification_evidence` (per-check results), `verified_at`, `pipeline_version`.
- `corpus_acceptance.py` change: in real mode it accepts `machine_verified` sources and provisions only if their evidence passes the rules below. It still fails closed otherwise. Keep `human_verified` working for the future. Show the diff to Mri before merging.
- Citable = `machine_verified` or `human_verified`. Everything else is uncitable.
- Add setting `CORPUS_TRUST_LEVEL = machine | human` (default `machine` for this submission). Banner text shows the level in force.

## Provision passes only if ALL checks agree (any failure -> `rejected`, with reason)
V1 Two independent extractions: (a) the PDF text layer, (b) OCR of the rendered page (install Tesseract or an OCR library; if no OCR engine can be installed, STOP and report BLOCKED. Do not weaken this to a single method). Normalise whitespace and compare word by word. Allowed difference: whitespace and ligatures only. Any word or number difference -> rejected.
V2 Number inventory: all digits, dates, rupee amounts, section/rule references must match exactly across V1 (a) and (b). Zero tolerance.
V3 Document integrity: the source file hash equals `manifest.json`, and `manifest.json` hashes equal the downloaded originals. `text_integrity_flags()` must be clean for that source.
V4 Metadata evidence: every date, G.S.R. number and effective date has a quoted string and page from the document that appears verbatim in the OCR text. No quote -> value is `not_stated`, never inferred. A source with `not_stated` effective date can only be `uncertain` validity and is rejected for the gate.
V5 Boundary check: the stored text starts and ends on the clause boundaries in the OCR page text, and the following sentence in the source does not begin with "provided that", "except", "explanation" or "subject to". If it does, merge the proviso into the provision or reject it. Never store a provision with a trailing proviso cut off.
V6 Version check: the amendment chain for the source is recorded from the manifest. Sources with `known_gaps` that affect the provision (for example the Consumer Protection Act, pending the Jan Vishwas Act 2026 schedule check) are `machine_verified` only for the parts proven unaffected; otherwise they stay `unverified` and uncitable. State the gap in the UI.
V7 Second-model check (optional, only if Kaggle LLM is up): ask the LLM, with temperature 0, to restate the clause in a fixed JSON schema (days, amounts, parties, exceptions). The values must equal the V2 inventory. An LLM disagreement can only reject, never approve.

## Conditions without a human
- Conditions are generated by the agent only from a quoted source phrase; no quote -> invalid.
- Each condition must pass a machine test table: for 3 synthetic fact sets (applicable, not applicable, unknown), the evaluator output must match the expected value that is derived from the quote by the rule itself, not from the LLM.
- Condition status `machine_verified` if it passes. Otherwise provision applicability is `unknown`.
- A provision whose conditions are not machine_verified is background only and cannot be the sole basis of any outcome.

## Selection without a human
Machine-verify only this core set first, then stop: all ECR_2020 and ECR_2021_AMENDMENT provisions, CPA §2(11), §35, §38, §39 (the CPA ones only if V6 allows), JUR_2021 if time remains. Do not machine-verify all 149. Do not claim coverage of anything not verified.

## Evaluation without a human
- Gold labels cannot come from the retriever or the answering LLM. Allowed: derive a gold label from a rule applied to the provision text and the story's quoted facts, e.g. a provision is gold relevant only if the story contains the fact fields its machine_verified conditions require. Mark these rows `labeling_status: "machine_derived"` and never present them as human labels. Report metrics separately and say they are machine-derived.
- If a row cannot be derived by rule, leave it unlabeled and excluded. Print the row counts in every table.

## Controls that stay in force (from AGENT_RISK_CONTROLS.md)
C7 gate protection, C8 answer-time guards (any unsupported section number blocks the answer), C9 evaluation honesty, C4 version tests. The only change is that approval comes from the machine pipeline above.

## Mandatory disclosure in submission
`SUBMISSION_NOTES.md` and the UI must state: the corpus was verified by an automated pipeline (two independent extractions, number inventory, boundary and version checks); it has not been reviewed by a human or a lawyer; the checks cannot catch an official document that is itself wrong or a legal interpretation error; known gaps; the Consumer Protection Act status. State the residual risks plainly. Do not call the product legal advice.
